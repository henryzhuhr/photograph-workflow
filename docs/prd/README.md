# Photograph Workflow PRD

## 结论

这个流程整体合理，适合做成一个轻量但可靠的照片工作流工具。推荐的关键顺序是：

1. 将相机存储卡中的 RAW 文件导入电脑。
2. 人工或半自动完成目录分类，并给目录命名。
3. 在 Lightroom 导入前，根据目录和自定义命名规则批量重命名 RAW/DNG 文件。
4. 将整理后的目录导入 Adobe Lightroom 进行筛选、评级和修图。
5. 从 Lightroom 导出成片。
6. 对当前拍摄项目目录打包压缩，写入归档位置。

其中最重要的边界是：文件重命名必须发生在 Lightroom 导入前。如果已经导入 Lightroom 后再改名，Lightroom catalog 可能会丢失原始文件引用，后续修图和导出会变得不稳定。

## 产品目标

本项目要解决的是摄影后期前后的“文件管理可靠性”问题，而不是替代 Lightroom 的修图能力。

实现形态明确为 uv 管理的 Python 脚本项目，优先服务本地文件扫描、重命名预览、重命名执行和归档。当前版本不要求安装成系统 CLI，用户可以直接执行 `.py` 脚本。

长期方向上，这套工作流可能扩展为电脑 Web 端、macOS 端和 iOS 端应用，也可能扩展到 Capture One 等其他后期软件。当前版本不实现这些应用形态，也不支持 Lightroom 之外的后期软件；但产品设计、数据契约和核心逻辑边界必须避免和单一脚本入口强绑定，保证后续可以复用同一套扫描、命名、校验和归档规则。

核心目标：

- 降低从相机导入到归档之间的重复手工操作。
- 保证 RAW/DNG、sidecar、归档包之间的命名和目录关系清晰可追踪。
- 在真正修改文件前提供预览、冲突检查和回滚依据。
- 支持按个人习惯自定义命名格式，而不是强制固定模板。
- 保持核心工作流可被脚本、桌面应用、Web 应用和移动应用复用。

## 目标用户

- 个人摄影爱好者：希望快速整理日常拍摄、旅行、家庭和活动照片。
- 半职业摄影师：需要按客户、日期、场景或项目组织素材，并长期归档。
- Lightroom 用户：保留 Lightroom 作为修图和导出工具，只自动化其前后的文件管理流程。

## 不做什么

当前版本不做这些事情：

- 不替代 Adobe Lightroom 的修图、评级、预设管理和导出引擎。
- 不直接修改 RAW 图像内容。
- 不默认上传云端或做多人协作。
- 不强制用户采用单一目录结构。
- 当前版本不提供电脑 Web 端、macOS 端或 iOS 端应用界面。

## 建议的信息架构

一个典型项目目录可以是：

```text
.
└── Photograph-Raw
    └── Travel
        ├── Shanghai
        │   ├── 20260101-上海东方明珠
        │   │   ├── .metadata.json
        │   │   ├── 20260101-上海东方明珠-080001_DSC00000.ARW
        │   │   ├── 20260101-上海东方明珠-080001_DSC00000.XMP
        │   │   └── 20260101-上海东方明珠-080001_DSC00000.JPG
        │   └── 20260101-武康路
        │       ├── .metadata.json
        │       └── 20260101-武康路-080002_DSC00001.ARW
        ├── Nanjing
        │   ├── 20260101-中山陵
        │   │   ├── .metadata.json
        │   │   └── 20260101-中山陵-080003_DSC00002.ARW
        │   ├── 20260101-夫子庙秦淮河
        │   │   ├── .metadata.json
        │   │   └── 20260101-夫子庙秦淮河-080004_DSC00003.ARW
        │   └── 20260101-南京长江大桥
        │       ├── .metadata.json
        │       └── 20260101-南京长江大桥-080005_DSC00004.ARW
        └── HongKong
            ├── 20260101-维多利亚港
            │   ├── .metadata.json
            │   └── 20260101-维多利亚港-080006_DSC00005.ARW
            ├── 20260101-HongKong_Victoria_Peak
            │   ├── .metadata.json
            │   └── 20260101-HongKong_Victoria_Peak-080007_DSC00006.ARW
            └── 20260101-中环街市
                ├── .metadata.json
                └── 20260101-中环街市-080008_DJI_00000.DNG
```

命名约定建议：

- 原始照片根目录使用 `Photograph-Raw`。
- 上层分类目录可以按个人习惯使用 `Travel`、`Shanghai`、`Family` 等普通容器名。
- 真正包含照片的目录使用 `{YYYYMMDD}-标题`，例如 `20260101-上海东方明珠`。
- `TODO` 目录可以作为待整理区，默认不参与重命名。
- `.metadata.json` 只放在真正包含照片文件的目录下，不要求顶层项目目录维护元数据。

工具不应强行搬迁已有目录。它应该读取用户指定的“项目目录”，递归识别其中的 RAW/DNG 和 sidecar，并在照片文件所在目录维护 `.metadata.json`。

## 核心原则

- 先预览，后执行：重命名、移动、压缩前必须可以 dry-run。
- 可追踪：每个照片目录维护 `.metadata.json`，记录命名配置、状态和文件映射；其中 `original_name` 不可变，便于排查和回滚。
- 不破坏 Lightroom：进入 Lightroom 之前完成路径和文件名稳定化。
- Sidecar 同步：同 stem 的 `.xmp`、`.acr`、`.jpg`、`.jpeg` 要跟随 RAW/DNG 处理；孤立 JPEG 不独立处理。
- 跨相机兼容：RAW 扩展名不能只假设一种格式。
