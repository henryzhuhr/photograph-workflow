# macOS 与桌面包装 App 设计

## 背景

当前本地 Web UI 已经可以承载可视化工作流，但浏览器和 Docker 环境不能安全地把 Finder 系统目录选择器返回的绝对路径直接交给本地服务。用户仍需要粘贴完整目录路径，这不符合长期桌面应用体验。

为了解决本地目录授权、最近工作目录、Finder 集成和桌面打包问题，后续可以建设两类桌面入口：

- macOS 原生 App：使用 SwiftUI / AppKit，直接调用 Finder 目录选择器并获取 security-scoped directory URL。
- 桌面包装 App：使用 Tauri 或 Electron 复用现有 Web UI，通过桌面壳调用系统目录选择器和本地能力。

本文只描述产品设计，不要求当前实现代码。

## 产品目标

桌面应用要解决的是“本地照片工作流的桌面体验”，不是重新定义扫描、重命名、sidecar、回滚和归档规则。

目标：

- 允许用户通过系统目录选择器选择照片项目目录。
- 记住用户授权过的最近工作目录，下次打开可以直接加载。
- 在桌面窗口中完成扫描、重命名预览、执行确认、回滚和归档。
- 支持打开 Finder、复制推荐压缩包名、查看 `.metadata.json` 相关状态。
- 保持与 Python 脚本、本地 Web UI 完全一致的命名和校验规则。
- 为未来 iPad App、iPhone App 和 Swift 侧核心逻辑复用保留空间。

## 路线一：macOS 原生 App

macOS 原生 App 是长期体验最好的形态。

适合解决：

- Finder 原生目录选择。
- sandbox 下的目录授权。
- security-scoped bookmark 持久化。
- 最近工作目录。
- 菜单栏、快捷键、通知、系统外观和窗口状态。
- 更自然的拖拽目录、Reveal in Finder、打开 Lightroom 辅助动作。

原生 App 的推荐体验：

1. 用户打开 App。
2. 点击选择目录，系统弹出 Finder 目录选择器。
3. App 获取用户授权的目录 URL，并保存可恢复的授权记录。
4. App 展示工作流时间线：选择目录、扫描、重命名、Lightroom 后期、归档。
5. 用户先生成计划，再确认执行任何文件修改。
6. 执行完成后展示结果和可回滚信息。

原生 App 不应在早期重写全部业务规则。核心规则尚未稳定前，macOS 原生层只负责 UI、权限、窗口和系统集成；扫描、命名、校验和归档仍应复用现有核心能力或共享契约。

## 路线二：桌面包装 App

桌面包装 App 是更快落地的桌面路线。

可选技术：

- Tauri：优先推荐。体积更小，适合把现有 Web UI 包装成桌面应用，并通过原生 bridge 调用系统目录选择器。
- Electron：生态成熟，调试和集成成本低，但包体和运行时成本更高。

桌面包装 App 的核心价值是复用当前 Web UI，同时补齐浏览器做不到的本地能力：

- 系统目录选择器。
- 保存最近目录。
- 打开 Finder。
- 调用本地 Python 服务或核心用例。
- 本地打包和分发。

桌面包装 App 应保持一个清晰边界：Web 前端只做展示和交互，桌面壳只做本地系统能力，业务规则仍由 Python application 层或未来共享核心提供。

## 推荐演进顺序

推荐先做桌面包装 App，再做完整原生 macOS App。

```text
本地 Web UI 已存在
        ↓
抽稳定的本地 API 与结构化计划契约
        ↓
Tauri 桌面包装 App，解决目录选择和桌面打包
        ↓
沉淀 contracts 与真实目录 smoke test
        ↓
SwiftUI 原生 macOS App，逐步承接更原生的桌面体验
        ↓
Swift Package / iPad App / iPhone App 复用稳定规则
```

这样可以先解决当前最大体验问题：浏览器无法自然选择本机目录。同时避免在核心规则还在演进时，把同一套重命名规则重复实现成 Python、JavaScript 和 Swift 三份。

## 目录授权与最近工作目录

桌面应用必须把“用户选择过的目录”作为授权对象，而不是只把绝对路径当作普通字符串。

产品语义：

- 第一次使用时，用户必须通过系统目录选择器授权目录。
- 授权成功后，该目录进入最近工作目录列表。
- 下次启动时，App 可以尝试恢复授权并加载该目录。
- 如果目录移动、删除或授权失效，App 必须提示用户重新选择。
- 用户可以从最近工作目录中移除记录。

不同技术路线的实现方式可以不同，但用户可见行为必须一致。

## 工作流界面要求

桌面应用应延续当前 Web UI 的工作流时间线：

1. 选择目录。
2. 扫描素材。
3. 重命名 RAW/DNG 与同名 sidecar。
4. Lightroom 后期。
5. 归档或生成推荐压缩包名。

每个阶段都必须展示：

- 当前阶段目的。
- 会读取或修改哪些文件。
- 是否会真正写入磁盘。
- dry-run 计划。
- 错误、警告和跳过原因。
- 执行完成后的结果。

重命名阶段必须继续提供命名模板占位符选择，而不是只依赖用户手写模板。

## 跨入口一致性

无论入口是 Python 脚本、本地 Web UI、桌面包装 App、原生 macOS App、iPad App 还是 iPhone App，都必须保持：

- `{date}` 只来自照片元数据，读取失败必须报错。
- 默认模板为 `{date:YYYYMMDD}-{title}-{date:HHMMSS}_{original}`。
- `.metadata.json.files[].original_name` 一旦记录不可修改。
- 只同步处理与 RAW/DNG 同 stem 的 `.xmp`、`.acr`、`.jpg`、`.jpeg`。
- 不写 RAW/DNG 元数据。
- 执行重命名、回滚和归档前必须先生成计划。

## 当前不做

当前设计阶段不做：

- 不实现 macOS App 代码。
- 不实现 Tauri / Electron 包装代码。
- 不迁移 Python 核心逻辑到 Swift。
- 不实现 iPad App。
- 不实现 iPhone App。
- 不接入 Capture One。
- 不改变现有脚本和 Web UI 的业务规则。

## 决策建议

如果目标是尽快解决“选择本地目录不自然”的问题，优先做 Tauri 桌面包装 App。

如果目标是长期最好的 macOS、iPadOS 和 iOS 生态体验，保留 SwiftUI 原生 App 方向，但应等数据契约、核心规则和真实目录测试更稳定后再开始实现。
