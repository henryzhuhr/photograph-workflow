# 用户旅程与交互设计

## 定位

UX 不只是界面摆放，还需要描述用户如何完成任务、每一步系统如何反馈、哪些操作需要确认、哪些错误会阻止继续。

Photograph Workflow 的 UX 文档需要同时覆盖：

- 信息架构：用户看到哪些区域、阶段和状态。
- 用户旅程：用户从导入 RAW 到归档的完整路径。
- 交互规则：哪些元素可点击，点击后发生什么。
- 状态变化：空状态、扫描中、可执行、警告、错误、完成。
- 安全确认：真正改文件前必须如何预览和确认。

## 主旅程

### 旅程总览

| 阶段 | 用户目标 | 主要交互 | 系统反馈 | 继续条件 |
| --- | --- | --- | --- | --- |
| 1. 准备项目 | 选择已分类目录 | 系统目录选择器、最近项目 | 显示路径、授权状态、可访问性 | 目录可读写 |
| 2. 检查素材 | 理解素材状态 | 扫描、展开问题目录 | RAW/DNG 数量、sidecar、跳过项、阻塞错误 | 无阻塞错误 |
| 3. 命名规则 | 确认模板和目录标题 | 点击占位符、编辑 title、查看样例 | 模板合法性、目录级 title、目标文件名样例 | 模板合法且 title 完整 |
| 4. 执行重命名 | 确认可写入计划 | 查看 dry-run、二次确认 | 原名到目标名映射、sidecar 映射、冲突列表 | 用户确认且无冲突 |
| 5. Lightroom 后期 | 完成修图流程 | 离开 App 到 Lightroom，完成后返回 | checkpoint 提示，不读取 catalog | 用户标记后期完成 |
| 6. 归档 | 长期保存项目 | 复制推荐名称或执行 ZIP 计划 | 推荐压缩包名、归档 dry-run、输出路径 | 用户确认归档方式 |

这张表是评审 UX 的主线。任何界面元素都应该能落回其中一个阶段；不能落回主旅程的入口，应放入设置、安全中心或后续版本。

### 1. 准备项目

用户目标：选择一个已经手工分类好的照片项目目录。

交互：

- 桌面端通过系统目录选择器选择项目根目录。
- App 显示当前项目路径和最近项目入口。
- 如果授权过该目录，下次打开可自动恢复。

系统反馈：

- 显示目录可访问。
- 显示最近项目保存状态。
- 如果目录不可访问，提示重新选择。

### 2. 检查素材

用户目标：确认目录里有哪些 RAW/DNG、sidecar 和问题文件。

交互：

- 用户点击扫描或进入项目后自动扫描。
- 默认展示目录级摘要，不先展示几百个文件明细。
- 用户可以展开问题目录查看具体文件。

系统反馈：

- 展示 RAW/DNG 数量、sidecar 数量、跳过文件和阻塞错误。
- 元数据读取失败时标记为阻塞错误。
- 只把与 RAW/DNG 同 stem 的 `.xmp`、`.acr`、`.jpg`、`.jpeg` 作为 sidecar。

### 3. 命名规则

用户目标：确认项目级命名模板和每个照片目录的标题。

交互：

- 用户通过内置占位符按钮插入 `{date:YYYYMMDD}`、`{title}`、`{date:HHMMSS}`、`{original}`。
- 用户可以覆盖某个目录的 `title`，覆盖值写入该目录 `.metadata.json`。
- App 展示实时样例，但不修改文件。

系统反馈：

- 展示模板是否合法。
- 展示每个目录将使用的 title。
- 如果某目录不符合规则，阻止生成可执行计划。

### 4. 执行重命名

用户目标：在真正改文件前确认完整 dry-run 计划。

交互：

- 用户生成重命名计划。
- 用户查看原文件名、目标文件名、sidecar 映射、冲突和错误。
- 用户二次确认后才执行。

系统反馈：

- dry-run 阶段不写入磁盘。
- 执行前写入 pending `.metadata.json`，确保可追踪。
- 执行后展示成功、失败和可回滚状态。

### 5. Lightroom 后期

用户目标：在后期软件中完成筛选、评级、修图和导出。

交互：

- App 只作为 checkpoint，不读取 Lightroom catalog。
- 用户确认自己已经完成后期，再回到 App 继续归档。

系统反馈：

- 提醒用户重命名应发生在 Lightroom 导入前。
- 不自动打开或修改 Lightroom 数据。

### 6. 归档

用户目标：把项目目录压缩并长期保存。

交互：

- 用户可以复制推荐压缩包名称，手动用 Keka 等工具压缩。
- 用户也可以执行 App 内 ZIP 归档计划。
- 用户可以配置默认 exclude 规则。

系统反馈：

- 推荐归档名包含时间戳。
- App 内归档必须先生成 dry-run 计划。
- 完成后展示输出路径和归档摘要。

## 异常旅程

异常旅程不是错误弹窗文案的补充，而是主旅程的一部分。它们决定用户是否可以继续、应该回到哪一步、系统是否允许写文件。

### 元数据不可读

- 系统必须提示 RAW/DNG 可能损坏或元数据不可读。
- 依赖 `{date}` 的重命名必须停止。
- 不使用文件创建时间或目录日期兜底。

### 文件名冲突

- dry-run 阶段展示冲突文件。
- 冲突未解决前不能执行重命名。

### sidecar 缺失

- `.xmp`、`.acr` 和机内 JPEG 都是可选 sidecar。
- 缺失不阻止 RAW/DNG 重命名。
- 只处理与 RAW/DNG 同 stem 的 sidecar。

### 目录授权失效

- 桌面或移动端 App 必须提示重新选择目录。
- 不允许仅凭历史绝对路径继续写文件。

## 原型交互层级

当前 UX 原型采用轻量交互，不连接后端、不执行文件操作。

可交互内容：

- Desktop / iPad / iPhone 视图切换。
- 配色方案切换。
- Desktop 左侧工作流阶段点击。
- iPad 左侧工作流阶段点击。
- iPhone 横向流程胶囊点击。
- Desktop、iPad 和 iPhone 主按钮模拟进入下一阶段。
- 当前阶段标题、说明、状态、下一步动作和用户旅程说明会随点击变化。

不可交互内容：

- 不打开真实系统目录选择器。
- 不读取真实 RAW/DNG。
- 不生成真实 dry-run 计划。
- 不写入 `.metadata.json`。
- 不执行重命名、回滚或归档。

这个层级适合在实现前评审用户路径、信息层级和危险操作确认流程。进入真实开发时，再把这些交互绑定到 application 用例和结构化计划对象。

## 注解规范

原型和文档中的 UX 注解应说明以下内容：

- 用户目标：用户为什么进入这个阶段。
- 触发动作：用户点击什么、选择什么或确认什么。
- 系统反馈：操作后界面必须展示什么状态。
- 安全门槛：什么时候必须 dry-run、二次确认或阻止继续。
- 异常路径：失败时停在哪一步，是否允许重试，是否允许跳过。
- 跨端差异：Desktop、iPad、iPhone 的交互可以不同，但必须表达同一条业务旅程。

注解不应该只解释视觉样式，例如“这个按钮是蓝色”。只有当视觉选择影响用户决策、安全确认或状态识别时，才需要写入 UX 注解。
